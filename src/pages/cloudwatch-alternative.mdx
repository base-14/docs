A platform team ran their payments API on AWS and their fraud
detection service on GCP. When checkout latency spiked on a Friday
evening, they opened CloudWatch. The AWS services looked normal, with
latency within bounds and error rates flat. Customers were still
complaining.

It took the team a while to check the GCP console. The fraud
detection service was timing out on a database connection pool, on
infrastructure that wasn't reporting to CloudWatch.

If you're evaluating a CloudWatch alternative, it's probably not
because CloudWatch doesn't work for the AWS resources it monitors. It
works well there. It's usually because the stack now reaches past
AWS, or because the bill has several meters that each grow on their
own.

## Why engineering teams outgrow CloudWatch

CloudWatch collects basic metrics from AWS services automatically, at
no charge and with no setup. Cross-account observability has no
additional charge, and alarms drive Auto Scaling and other AWS
actions directly. For a team fully on AWS at modest scale, it's a
reasonable default. Teams outgrow it for a few structural reasons,
usually once they need
[unified observability](/blog/unified-observability) across the
whole stack.

### Automatic coverage stops at the AWS boundary

CloudWatch monitors AWS resources natively. Outside AWS it can still
take data: the CloudWatch agent runs on-premises and on other clouds,
CloudWatch accepts OTLP for traces, logs and metrics, and it can query
Azure Monitor and Prometheus through Lambda-based connectors. But
outside AWS you deploy and run that collection yourself, and other
clouds' managed services don't report in automatically.

When a problem crosses cloud boundaries, like the checkout outage
above, engineers switch between CloudWatch, GCP's Cloud Monitoring
and whatever they've assembled for on-prem services. Each has its own
query language, dashboard conventions and retention policies. That is
how teams end up with
[observability theatre](/blog/observability-theatre): plenty of
dashboards, no single view of the system.

### Separate meters for log ingestion, storage and queries

CloudWatch Logs bills log data at several stages, and alarms add a
fee of their own:

| Charge                  | Rate                                                                                                                                          | What you're paying for       |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------- |
| Ingestion               | [$0.50/GB](https://aws.amazon.com/cloudwatch/pricing/) for custom logs; vended logs from AWS services tier down to $0.05/GB above 50 TB/month | Getting data into CloudWatch |
| Storage                 | $0.03/GB/month (on compressed data)                                                                                                           | Keeping it there             |
| Queries (Logs Insights) | $0.005/GB scanned                                                                                                                             | Looking at it                |
| Alarms                  | $0.10-$0.50 per alarm per month                                                                                                               | Being notified               |

The first 5 GB of log data a month is free across ingestion, storage
and data scanned. The Infrequent Access log class halves custom log
ingestion to $0.25/GB, with a reduced feature set. Vended logs, the
logs AWS services such as VPC Flow Logs publish, are priced at
$0.50/GB for the first 10 TB a month, $0.25/GB for the next 20 TB,
$0.10/GB for the next 20 TB and $0.05/GB above 50 TB. Logs your
applications send are custom logs and stay at $0.50/GB at any volume.

Storage is charged on compressed data (AWS assumes about 0.15 bytes
stored per byte ingested), so keeping logs costs far less per raw GB
than ingesting them. Storage is cumulative, though. Log groups
default to "Never expire", so each month's logs add to the bill until
someone sets a retention policy.

For a team generating 100 GB of logs per day, here's what the
[CloudWatch bill](https://aws.amazon.com/cloudwatch/pricing/)
looks like after six months:

- **Ingestion**: 100 GB × 30 days × $0.50 = $1,500/month.
- **Storage** (cumulative, ~3 TB compressed after 6 months):
  ~$90/month, rising each month.
- **Queries** (20 queries/day scanning 500 GB each): ~$1,500/month.
- **Total**: about $3,100/month for logs alone.

Logs Insights bills per GB scanned, so wide queries across large log
groups during an incident carry a cost. Scout's
[signal-based pricing](/observability-cost-optimization) is a
$250/month platform fee plus $0.10/M metrics and $0.25/M logs &
traces, with storage and queries included.

### Several products, each priced and queried separately

AWS's observability stack is a set of products that share the
CloudWatch console:

- **CloudWatch Metrics** for infrastructure and custom metrics.
- **CloudWatch Logs** for log management.
- **AWS X-Ray and Transaction Search** for distributed tracing.
- **Application Signals** for application performance monitoring
  (APM): service maps, latency and error metrics, and service level
  objectives (SLOs).
- **CloudWatch RUM, Synthetics and Internet Monitor** for user and
  connectivity monitoring.

Application Signals links traces, metrics and logs for instrumented
services, so AWS does have an APM. Each product is still priced on its
own meter, and queries are split across Logs Insights, Metrics
Insights, PromQL for OpenTelemetry metrics, and X-Ray's trace
filters. Correlating data outside what Application Signals covers
means matching timestamps and trace IDs across those surfaces.

### Custom metrics priced per series

CloudWatch charges custom metrics per metric per month: $0.30 each
for the first 10,000, $0.10 for the next 240,000, $0.05 for the next
750,000 and $0.02 above 1,000,000. Every unique combination of
namespace, metric name and dimension values is a separate billable
metric. Adding a single high-cardinality dimension like `user_id` or
`request_id` turns one metric into thousands.

Converted to data points, a metric reporting every 60 seconds sends
about 43,200 points in a 30-day month. At $0.30 that is about $6.94
per million points, falling to about $2.31, $1.16 and $0.46 per
million at the lower tiers. A metric reporting every 10 seconds sends
259,200 points for the same monthly charge, about $1.16 per million at
the first tier. Metrics published with PutMetricData also pay for API
requests beyond the first million a month, and metrics sent as
Embedded Metric Format log lines pay $0.50/GB log ingestion on top.
Scout charges $0.10 per million points for every metric.

A team with 50 services emitting 20 metrics each across 5
environments and 3 regions reaches 15,000 custom metrics. At $0.30
for the first 10,000 and $0.10 after that, the metric charge alone is
$3,500/month.

CloudWatch now has a second path. OpenTelemetry metrics sent over
OTLP, generally available since June 2026, are billed at $0.50 per GB
ingested with no per-series charge and 15 months of storage included.
AWS puts a typical data point at 300-600 bytes, which works out to
about $0.15-$0.30 per million points. PromQL queries through the API
cost $0.01 per million samples scanned; console and dashboard queries
are free.

### Dashboards and alarms

CloudWatch dashboards cost $3 per dashboard per month after the first
three. Basic monitoring for AWS services reports every 5 minutes;
detailed monitoring reports every minute and is billed at custom
metric rates. Custom metrics can report down to 1 second.

Alarms cost $0.10 per alarm metric per month at standard resolution,
$0.30 at high resolution and $0.50 per composite alarm. CloudWatch
supports anomaly detection alarms, billed as three alarm metrics each
to cover the model's upper and lower bands. Log query and PromQL
alarms add query charges on each evaluation.

## What to look for in a CloudWatch alternative

Before comparing tools, decide what AWS monitoring beyond CloudWatch
means for your team. A CloudWatch replacement should provide:

- **Multi-cloud visibility**: AWS, GCP, Azure and on-prem
  infrastructure in one view.
- **Unified signals**: Logs, metrics and traces in a single query
  surface.
- **APM**: Transaction tracing, service maps and error tracking in
  the same place as logs and metrics.
- **Predictable pricing**: A bill you can forecast before the month
  starts, without a per-GB charge on queries.
- **[OpenTelemetry](https://opentelemetry.io/docs/) support**:
  Vendor-neutral instrumentation that keeps your telemetry portable.
- **Meaningful retention**: At least 30 days of full-resolution
  data, with options for longer.

### Pricing: separate meters vs one rate per signal

CloudWatch charges to ingest logs, store them and query them, and
prices custom metrics per series per month. A custom metric reporting
every 60 seconds costs about $6.94 per million points at the first
tier, or about $0.15-$0.30 per million points through the OTLP path.

Signal-based pricing uses two rates: $0.10 per million metrics,

### Retention: longer for metrics

CloudWatch keeps metrics for 15 months, at 1-minute resolution for 15
days, 5-minute for 63 days and 1-hour for 455 days. Log retention is
set per log group and defaults to never expire, billed per GB stored.
X-Ray keeps traces for 30 days. Scout keeps 30 days of full-resolution

### Scope: automatic coverage stops at the AWS boundary

CloudWatch covers AWS services automatically. Other clouds and
on-prem can send data through agents or OTLP senders you run, but

### Tracing: X-Ray vs native distributed tracing

X-Ray and Transaction Search are priced apart from CloudWatch Logs
and Metrics. X-Ray bills $5 per million traces recorded. With
Transaction Search, spans are billed at $0.35/GB ingested for the
first 10 TB, and 1% are indexed as trace summaries at no charge, with
$0.75 per million beyond that. Application Signals links traces to
logs and metrics for instrumented services.

AWS is moving X-Ray to OpenTelemetry. The X-Ray SDKs and daemon

means no rework later, whichever backend you choose.

In Scout, traces, logs and metrics share a single data lake. A slow
trace shows the associated log entries and infrastructure metrics in
the same view.

## Migration: from CloudWatch to base14 Scout

Migrating to a CloudWatch alternative doesn't require a flag-day
cutover. OpenTelemetry makes it a gradual process.

### Deploy OpenTelemetry collectors

Install
[OpenTelemetry Collectors](/instrument/collector-setup/otel-collector-config)
on your infrastructure. They run alongside existing CloudWatch
agents. Nothing changes for your current monitoring. For a detailed
setup guide, see
[building a production-ready OTel collector](/blog/production-ready-otel-collector).

### Point the collector at Scout

Configure the collectors to export to Scout. Keep a copy flowing to
CloudWatch during the transition; the collector supports multiple
exporters. For AWS-native metrics, see
[AWS CloudWatch to Scout](/instrument/infra/aws/cloudwatch-metrics/aws-cloudwatch-overview).

### Run both in parallel

Run both platforms side by side for 2-4 weeks. Rebuild the
dashboards and alert rules your team relies on, and confirm Scout
answers the questions CloudWatch, X-Ray and GCP monitoring answer
today. base14's onboarding team works with your engineers during the
first month, at no cost.

### Decommission the CloudWatch agent and X-Ray daemon

Once confident, remove redundant agents and scale down CloudWatch
spend. If you still run the X-Ray SDKs or daemon, this is the point to
retire them instead of migrating twice. Your OpenTelemetry
instrumentation stays yours either way.

The migration takes 4-6 weeks for a mid-size team (~100 services).
Teams that already use OpenTelemetry move faster because the
instrumentation is in place.

## Who should switch (and who shouldn't)

### Switch to base14 Scout if

- **You run multi-cloud or hybrid infrastructure.** CloudWatch's
  automatic coverage stops at AWS. Scout treats every environment the
  same way.
- **Your CloudWatch bill keeps growing.** Log storage accumulates,
  queries bill per GB scanned, and custom metrics bill per series.
  Scout bills per signal.
- **You want standard SQL across traces, logs and metrics.** On
  AWS they are spread across X-Ray, Logs Insights and Metrics Insights
  or PromQL.
- **You still run the X-Ray SDKs or daemon.** They reach end of
  support on February 25, 2027, so the move to OpenTelemetry is coming
  either way.
- **You want portable instrumentation.** OpenTelemetry works with any
  OTLP-compatible backend.

### Stay on CloudWatch if

- **You're fully on AWS, at small scale, and the free tier covers
  you.** It includes 10 custom metrics, 5 GB of log data, 3 dashboards
  and 10 alarm metrics a month.
- **You already send metrics to CloudWatch over OTLP.** At $0.50/GB,
  about $0.15-$0.30 per million points with 15 months of storage, the
  case for switching is then the query surface and multi-cloud
  coverage, not metric price.
- **You need long metric history without paying for it.** CloudWatch
  keeps metrics for 15 months.
- **You depend on CloudWatch alarms for Auto Scaling and
  EventBridge.** Alarms act on AWS services directly. If these
  integrations are critical, keep CloudWatch for the trigger mechanism
  and use Scout for observability. They can coexist.
- **Your team has deep CloudWatch Logs Insights expertise.** Switching
  has a retraining cost. If your runbooks and on-call workflows
  reference specific CloudWatch queries, factor in the time to rebuild
  them.

### The hybrid approach

Many teams keep CloudWatch for AWS-native integrations, such as alarms
that trigger Auto Scaling or EventBridge rules, and route application
telemetry, other clouds and LLM telemetry through Scout.
OpenTelemetry instrumentation makes running both straightforward.
